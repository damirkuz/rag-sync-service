# Руководство по production-доработке

Этот репозиторий намеренно ограничивается интерфейсами и безопасными заглушками. На рабочем устройстве выполните следующие шаги:

1. Реализуйте `GitProviderClient`, например `GitLabGitProviderClient`, для сравнения commit, чтения файла и получения списка файлов. Замените `StubGitProviderClient`; комментарии `TODO(PRODUCTION)` показывают точки доработки.
2. Реализуйте `RagPlatformClient` с аутентифицированными вызовами upsert/delete и замените `StubRagPlatformClient`.
3. Перенесите `rag-sync.api-token` из локальной конфигурации в менеджер секретов или секрет развёртывания. При необходимости дополнительно проверяйте токен на сетевой границе.
4. Замените автоматическое создание репозиториев явной регистрацией или whitelist и задайте mapping «репозиторий → RAG collection».
5. Настройте Git job или webhook default branch, вызывающий `POST /api/v1/rag-sync/events/git` с общим токеном. Иллюстративный job приведён в корневом README.
6. Настройте production PostgreSQL через переменные окружения из `application-postgres.yaml` и сохраните историю миграций Flyway.
7. Добавьте структурированные логи, метрики, health checks, алерты и retry-политику, подходящие целевой платформе.
8. Если сервис будет запущен более чем в одном экземпляре, добавьте распределённый захват или блокировку по `repository_id + branch` перед обработкой job worker'ом.
9. Настройте `.rag-docs-hook.env` целевого репозитория. В `AGENT_SKILL_COMMAND` укажите настоящий вызов агента-документатора, а `RAG_DOCS_GENERATE_COMMAND` оставьте указывать на `run-agent-skill.example.sh` либо на переименованную production-обёртку.

Маркеры TODO намеренно находятся в stub-клиентах, автоматической регистрации репозиториев, обработке переименования и захвате job worker'ом. Не считайте БД сервиса или RAG-платформу источником истины: восстановление из Markdown default branch всегда должно оставаться возможным.
