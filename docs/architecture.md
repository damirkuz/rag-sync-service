# Архитектура

```text
Компьютер разработчика
  pre-commit hook -> внешний генератор -> docs/*.md
                                        ↓ commit в default branch
Git job/webhook -> rag-sync-service -> GitProviderClient -> Markdown конкретного commit
                                      -> RagPlatformClient -> внешний RAG-индекс
                                      -> PostgreSQL -> состояние job/документов/синхронизации
```

Markdown-файлы в `docs/` default branch являются источником истины. RAG-платформа — поисковая проекция этих файлов, поэтому её должно быть возможно полностью восстановить. БД сервиса тоже содержит производные данные: она обеспечивает идемпотентность, историю job и хеши, но не должна становиться каноническим хранилищем документации.

Pre-commit hook обеспечивает быструю локальную обратную связь. Он видит только staged-изменения в релевантных файлах и вызывает настраиваемый генератор; hook никогда не добавляет созданные файлы в Git автоматически. Удалённый побочный эффект — обновление RAG — выполняется сервисом только после появления commit в default branch.

Контроллер сервиса создаёт job со статусом `PENDING` и немедленно возвращает `202 Accepted`. Планировщик забирает job, через `GitProviderClient` сравнивает commit или получает список Markdown-файлов, а затем через `RagPlatformClient` добавляет, обновляет или удаляет документы. Только полностью успешная job меняет `rag_sync_state.last_successful_commit_sha`.

Каркас рассчитан на один экземпляр сервиса. Для нескольких production-реплик нужна распределённая блокировка по `repository_id + branch`; см. [руководство по доработке](extension-guide.md).
